# Thinking Lab

A growing collection of standalone thinking experiments. This is separate from the production tools repository. The second goal adds five experiments to the existing four.

Use plain HTML, CSS and ES modules. All deployable source lives in `dist/`; no external fonts, libraries, API calls, authentication or build step. Work in your assigned directory only. Shared files, gallery, hosting and vault notes belong to the parent agent.

Each experiment has `index.html`, `app.js`, `style.css` and a pure mechanism/state module if useful. Link `../shared/base.css` before local styles. Import `mountShell` from `../shared/shell.js` and call `mountShell({active: '<route>', label: 'MODEL 01', title: '…'})`. This inserts a small global header before page content. Shared helpers are `escapeHtml(value)`, `downloadText(filename,text,mime)`, `readStore(key,fallback)`, `writeStore(key,value)` in `../shared/utils.js`. You can use them or own equivalents. Prefix storage keys `thinking-lab:`. Pure modules use named ES exports. Node tests use built-in `node:test`, files `*.test.js` beside source, excluded from published directory later if necessary.

Visual direction: a crisp, generous working instrument. Cool pale canvas, white surfaces, navy ink, cobalt accent; teal and amber for meaningful states. System sans font, tabular numerals, strong readable hierarchy, no marketing hero wasting the first screen. Include a working example immediately. Use local CSS to give the actual interaction room. Desktop 1440px and phone 390px must work without page overflow. Inputs and controls must be keyboard accessible and have visible labels/focus. Respect reduced motion. No generic walls of equal cards.

Models compute outcomes from exposed mechanisms. Avoid scripted conclusions or claims of empirical prediction. Scaffolds accept the user's own material, preserve edits locally and export useful Markdown. All examples are fictional/generic. No employer information. Keep explanations short and near the relevant control.

Matthew specifically likes tactile interaction: moving, connecting, grouping, changing boundaries, steering and replaying should meaningfully affect the model or thinking. A canvas is useful when it supports those actions; avoid cosmetic dragging. Make the main working surface immediate. Include touch and keyboard/click alternatives, visible drop/selection states and undo/reset. Body text should be at least 16px and regular labels 14px; reserve smaller sizes for secondary metadata. Preserve all existing experiments and their stored work.

New routes: `teams`, `delay`, `reliability`, `constraints`, `analogy`. The parent updates gallery and shared navigation. A shared pointer helper is available: `attachCardDrag({root, itemSelector, handleSelector, dropSelector, onDrop})` from `../shared/drag.js`; onDrop receives `{itemId, dropId, item, drop, event}` from data-drag-id / data-drop-id. Set `touch-action:none` on drag handles only, and provide a labelled click/keyboard move alternative. The helper supports mouse/touch and adds `is-dragging`, `is-drop-target` classes. It returns a destroy function. It does not provide keyboard alternatives itself.

Run meaningful mechanism tests, document assumptions in a concise local README, and report limitations honestly. Do not ask a second agent to review your work. Do not change shared files or register/deploy Sites. Parent handles integration, browser verification and publication.
